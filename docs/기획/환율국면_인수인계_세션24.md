## 1. 절대 뒤집지 말아야 할 결정

1. `src/lib/fxRegime.ts` 판정 로직을 임의 변경하지 않는다.
2. 백테스트/미래 시뮬레이션은 반드시 `evaluateRegime(series.slice(0, i+1), ...)`를 사용한다.
3. 메디아나만 월 약 3.0M USD 순유입 구조가 확인됐다. 다른 법인에 일반화하지 않는다.
4. 정책표 숫자는 **환전 비율이 아니라 환전 후 남길 전사 외화 비중**이다.
5. 정책밴드는 특정 통화 비중이 아니라 **전 통화 외화자산 원화환산 합계 ÷ 전사 총자금**이다.
6. 정기예금은 만기 전 보유액/위험에는 포함하지만 환전 가능 재고에는 포함하지 않는다.
7. 정기예금 이자는 환차손익 원가에 섞지 않는다. 예상 이자는 별도 표시하고 실제 입금 시 신규 외화 로트로 잡는다.
8. 취득원가 이하 매도를 금지하지 않는다. 손실을 계산·표시하되 정책 상한/결제 버퍼 판단을 우선한다.
9. 프로덕션 Supabase는 SELECT만 허용. SQL은 문서로 제공하고 사용자가 SQL Editor에서 실행한다.

## 2. 최신 워크플로 — 전사 바구니에서 실제 환전까지

```text
전사 총자금
  ↓
모든 통화 외화 포트폴리오 원화환산 합계
  ↓ 정책밴드 및 수준×추세 목표와 비교
전사 기준 초과 환전 필요액 산출
  ↓
USD/EUR/JPY/GBP 통화별 환율 수준·국면 확인
  ↓
선택 통화의 보통예금 + 만기도래 정기예금만 집행 가능
  ↓
FIFO로 오래된 가용 로트부터 소진
  ↓
실현손익·잔존 장부환율·남은 평가손익 갱신
```

### 2.1 정책 분자·분모 SSOT

- 분자: `PolicyRealData.fxPortfolioHoldings`
  - 운전자금의 `daily.fx_usd` 등 통화별 **외화 원금**
  - 운용자금의 모든 외화 원금(가용/불가용 포함)
  - 통화별 현재 환율로 KRW 환산 후 합계
- 분모: `PolicyRealData.fxPolicyDenominator`
  - 원화 운전자금 + 운전자금 외화환산액
  - 가용/불가용 운용자금
  - 가용 국채와 가용 지분
- 비율: `fxPortfolioHoldings / fxPolicyDenominator × 100`

⚠ 과거 `FxRegimePage`는 `daily.fx_usd`를 KRW로 오인해 현재 환율로 다시 나누었다. 이는 수정됐다. `fx_usd` 등은 원금이고 `fx_krw`만 전 통화 운전자금 외화의 KRW 환산 합계다.

### 2.2 `최대 미환전 노출 한도`

- 사용자가 지적한 대로 고정 KRW 한도는 정책밴드 상한과 같은 위험을 이중 제한했다.
- 실시간 입력 화면에서 제거했고 `FxRegimeContext.maxExposureKRW`에는 `null`을 전달한다.
- 엔진 필드와 테스트는 과거 검증 호환 때문에 삭제하지 않았다.
- 백테스트 화면의 `최대 미환전 노출`은 **설정 한도**가 아니라 관측된 최대 잔고 KPI이므로 유지한다.

## 3. FIFO 원장과 정기예금

### 3.1 원장 필드

`fx_lots`에 다음 필드가 추가됐다.

- `account_type`: `demand_deposit | term_deposit`
- `annual_interest_rate`: 연이율 %, 0 이상
- `maturity_date`: 정기예금 필수, 취득일 이상

### 3.2 소진 규칙

- 보통예금: 즉시 FIFO 후보
- 정기예금: `maturity_date <= 거래일`일 때만 FIFO 후보
- FIFO 정렬: `acquired_date → created_at → id`
- 이미 소진 이력이 있는 로트는 수정/삭제 불가
- 완료 거래 취소는 `fx_lot_consumptions`을 원복하고 로트 잔액을 되돌린다.

### 3.3 원장 화면

경로: `/fx-ledger/:company?`

- 재고/매각 CSV 선택 및 미리보기
- 실제 저장은 사용자 확정 버튼을 눌렀을 때만 실행
- 숨김 file input + 명시적 `CSV 파일 선택` 버튼으로 파일창 오류 수정
- `표준 양식 다운로드` 제공
- 보유 로트 수정/삭제
- CSV 이관 과거 매각 수정/삭제
- 잔여 외화 / 현재 환전 가능 / 만기 전 잠금 / 예상 만기이자 / 장부환율 / 평가손익

### 3.4 CSV 표준 열

재고:

```csv
date,currency,accountType,amount,bookRate,annualInterestRate,maturityDate
2026-08-12,USD,demand_deposit,100000,1412.9,0,
2026-08-12,USD,term_deposit,1000000,1472.8,3.57,2026-09-11
```

매각:

```csv
date,currency,amount,acquisitionRate,saleRate
2026-08-12,USD,100000,1450.0,1500.0
```

### 5.1 ⛔ RPC 호출로 "적용 여부"를 확인하지 말 것 (2026-08-12 실사고 직전)

세션24 착수 시 SQL 적용 여부를 확인하려고 `supabase.rpc()`를 호출한 적이 있다.
"anon 권한이라 인증 체크에서 막힐 것"이라고 가정했으나 **틀렸다.**

- 개발용 브라우저에 **`admin@selvas.com` 실제 Supabase Auth 세션이 살아 있었다.**
- 그 결과 `auth.uid()` 검사와 `treasury_users` 권한 검사를 **모두 통과**해 함수 본문까지 실행됐다.
- 제로 UUID(`00000000-…`)를 넘겨 "찾을 수 없습니다"로 끝났을 뿐,
  **실제 UUID였다면 로트 삭제·환전 완료가 그대로 실행됐다.**

**규칙**
1. `complete_fx_trade_with_fifo` / `reverse_completed_fx_trade` /
   `update_unconsumed_fx_lot` / `delete_unconsumed_fx_lot` 를 **탐지 목적으로 호출 금지.**
   이들은 전부 쓰기 함수다.
2. 적용 여부는 **SELECT 로만** 확인한다.
   - 테이블/컬럼: `restSelect('fx_lots', { limit: 1 })` 로 컬럼 목록 확인
   - 함수 존재 여부까지 알아야 하면 **사용자에게 물어본다.** 추측하지 말 것.
3. 개발 브라우저에 관리자 세션이 있을 수 있다고 **항상 가정**하라.
   "권한이 없으니 안전하다"는 전제를 두지 말 것.

> 참고: `create or replace` 구조라 **함수가 존재해도 최신 버전인지는 알 수 없다.**
> 버전 확인은 사용자 확인이 유일한 방법이다.

### 8.3 🔴 실데이터 결함 3건 발견·수정 (2026-08-12)

등록된 60건을 CSV 원본과 대조하다 **환전 가능액을 과대 계산하는 결함**을 찾았다.

#### ① 계좌유형·이자율·만기가 컬럼에 반영되지 않음
초기 이관이 `account_type` 컬럼 도입 **이전**에 이뤄져, 값이 memo 텍스트로만 남았다.

```
memo: "2026-08-11 개시재고 · term_deposit · 만기 2026-09-11 · import-key:…"  ← 정보는 여기
account_type: demand_deposit / annual_interest_rate: 0 / maturity_date: null  ← 컬럼은 기본값
```

결과: **만기 전 정기예금 USD 6,000,000(약 85억원)이 "즉시 환전 가능"으로 집계**됐다.
- 2026-03-11 · 1,000,000 · 만기 2026-09-11 · 3.57%
- 2026-06-17 · 5,000,000 · 만기 2026-09-17 · 3.74%

→ `/fx-ledger` 에 **「계좌유형 교정」 버튼** 추가. CSV 를 기준으로 계좌유형·이자율·만기만
   되돌린다(금액·환율은 건드리지 않음). 계획을 먼저 보여 주고 사용자가 승인해야 실행된다.

#### ② 스키마에 없던 세 번째 유형 `mmda`
실제 CSV 구성: `demand_deposit` 14건 / **`mmda` 6건(USD 5,347,168.58)** / `term_deposit` 2건.
파서는 `mmda` 를 거부하도록 돼 있어 **같은 CSV 를 다시 올릴 수 없는 상태**였다.

→ MMDA(Money Market Deposit Account)는 **수시입출식이라 환전 가능성은 보통예금과 동일**,
   이자율만 붙고 만기는 없다. 스키마·파서·UI·FIFO 전부에 3종을 반영했다.
   **적용 필요 SQL: `docs/db/fx_lot_mmda_migration.sql`**

#### ③ 화이트리스트 방식이 만든 "조용한 잠금"
`isLotAvailable` 과 FIFO RPC 가 `account_type = 'demand_deposit'` 를 **화이트리스트**로 썼다.
그러면 새 유형이 추가될 때마다 `maturity_date` 가 null 이라 조건이 NULL 로 평가돼
**말없이 잠긴 것으로 취급**된다(환전 가능액 과소 계산).

→ 잠기는 유형(`term_deposit`)만 명시하는 **블랙리스트로 뒤집었다.**
   `LOCKED_ACCOUNT_TYPES` 상수로 SSOT 화. SQL 제약도 동일하게 수정.

#### ④ (부수 발견) CSV 재업로드 시 60건 중복 삽입 위험
memo 에 저장된 `import-key` 는 **5필드**인데 `inventoryKey` 가 언젠가 **7필드**로 확장되면서
기존 키와 절대 일치하지 않게 됐다. 그 상태로 같은 CSV 를 올리면 **60건이 통째로 중복 삽입**된다.

→ 중복 판정 전용 `inventoryMatchKey`(5필드) 신설. 이자율·만기는 교정 대상이라 키에서 제외.

**회귀 테스트 9건 추가** (`fxLots.test.ts` 4 / `fxCsvImport.test.ts` 5) → 전체 226 → **235건**.

## 10. 알려진 한계와 판단이 필요한 부분

- 전사 초과액의 통화간 자동 배분 규칙은 없다. 환율 국면, 결제 필요, 만기, 통화 집중도 중 무엇을 우선할지 정책 결정 필요.
- `fx_krw`와 통화별 `fx_usd/fx_eur/...` 환산 합계가 소수점/고시시점 차이로 완전히 같지 않을 수 있다. 정책 바구니는 통화별 원금×현재환율을 사용한다.
- 정기예금 예상 이자는 단리 `원금×연이율×일수/365`이며 실제 금융기관 일수계산/세전·세후와 차이가 날 수 있다.
- 국채·지분의 불가용 자산을 정책 총자금 분모에 포함할지에 대한 최종 회의체 정의는 확인 필요. 현재는 외화 비중 왜곡을 막기 위해 운용자금 가용/불가용을 모두 포함하고 국채·지분은 기존 가용 기준을 유지했다.
- 백테스트는 실적 재현이 아니라 규칙 비교 실험이다. 오늘 잔고를 과거 환율에 놓은 금액을 실제 과거 손익으로 해석하면 안 된다.
