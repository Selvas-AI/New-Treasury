## 0. ⛔ 가장 먼저 — 사용자가 아직 누르지 않은 버튼이 있다

**`/fx-ledger/메디아나` → 「교정 대상 확인」 → 「이 8건 교정 실행」**

이걸 실행하기 전까지 **만기 전 정기예금 USD 6,000,000(약 85억원)이 "즉시 환전 가능"으로
집계된다.** 환전 권고액이 그만큼 부풀려지므로, 이 상태로 다른 기능을 검증하면 안 된다.

```
현재:   환전 가능 14,088,438 / 만기 전 잠금 0
교정 후: 환전 가능  8,088,438 / 만기 전 잠금 6,000,000
```

- 실행은 **사용자만** 할 수 있다. 에이전트가 RPC 를 직접 호출하지 말 것(§4.1).
- 재고 CSV 를 먼저 선택하면 연이율(3.57 / 3.74 / 3%)까지 채워진다. 선택 안 해도 계좌유형·만기는 교정된다.
- 실행 후 위 숫자가 맞는지 화면에서 확인하고, 이어서 §5 로 넘어간다.

## 2. 세션24에서 고친 것 — 실데이터 결함 5건

DB 60건을 CSV 원본과 대조하다 발견했다. 전부 **환전 가능액을 왜곡**하는 결함이었다.

### ① 계좌유형·이자율·만기가 컬럼에 없고 memo 에만 있었다
초기 이관이 `account_type` 컬럼 도입 **전**에 실행돼, 60건 전부
`demand_deposit / 0 / null` 로 저장됐다. 원본은 memo 에 남아 있다.

```
memo: "2026-08-11 개시재고 · term_deposit · 만기 2026-09-11 · import-key:2026-03-11|USD|term_deposit|1000000|1472.8"
```

→ `intentFromMemo()` 로 복원. import-key 3번째 필드가 계좌유형이라 가장 신뢰할 수 있다.
   **연이율만 memo 에 없어 CSV 가 필요하다.**

### ② 스키마에 없던 세 번째 유형 `mmda`
실제 구성: `demand_deposit` 14 / **`mmda` 6(USD 5,347,168.58)** / `term_deposit` 2(USD 6,000,000).
파서가 `mmda` 를 거부해 **같은 CSV 를 다시 올릴 수 없었다.**

→ MMDA 는 수시입출식이라 **환전 가능성은 보통예금과 동일**, 이자율만 붙고 만기 없음.
   스키마·파서·입력 UI·FIFO 전부 3종 반영.

### ③ 화이트리스트가 만든 "조용한 잠금" ⭐
`isLotAvailable` 과 FIFO RPC 가 `account_type='demand_deposit'` 를 화이트리스트로 썼다.
새 유형은 `maturity_date` 가 null 이라 `maturity_date <= 거래일` 이 **NULL 로 평가**되어
경고 없이 잠긴다(환전 가능액 과소 계산).

→ 잠기는 유형만 명시하는 **블랙리스트로 반전**. `LOCKED_ACCOUNT_TYPES` 로 SSOT 화.
   **금지: `accountType === 'demand_deposit'` 형태의 가용성 판정을 되살리지 말 것.**

### ④ CSV 재업로드 시 60건 중복 삽입 위험
memo 의 `import-key` 는 **5필드**인데 `inventoryKey` 가 **7필드**로 확장돼 기존 키와
절대 일치하지 않았다. 그 상태로 같은 CSV 를 올리면 전량 재삽입된다.

→ 중복 판정 전용 `inventoryMatchKey`(5필드) 신설.
   **이자율·만기는 교정 대상이므로 판정 키에 넣으면 안 된다.**

### ⑤ `window.confirm` 이 차단되면 조용히 아무 일도 안 일어남 ⭐
크롬은 대화상자가 반복되면 "추가 대화상자 표시 안 함"으로 막고, 그때 `confirm()` 은
**즉시 false 를 반환**한다. 취소 분기에 메시지가 없어 **버튼만 깜빡이고 먹통처럼 보였다.**

→ 데이터를 바꾸는 조작은 **화면 안 미리보기 패널**로 승인받는다.
   **금지: 다건 변경·비가역 조작에 `window.confirm` 만 쓰지 말 것.**
   차단과 취소를 구분할 수 없고 사용자가 원인을 알 수 없다.

## 4. ⚠️ 절대 하지 말 것 (세션24에서 실사고 직전까지 감)

### 4.1 RPC 호출로 "SQL 적용 여부"를 확인하지 말 것
SQL 적용 확인을 위해 `supabase.rpc()` 를 호출한 적이 있다.
"anon 이라 권한 체크에서 막힌다"고 가정했으나 **틀렸다.**

- 개발 브라우저에 **`admin@selvas.com` 실제 Supabase Auth 세션이 살아 있었다.**
- `auth.uid()` 와 `treasury_users` 권한 검사를 **모두 통과**해 함수 본문까지 실행됐다.
- 제로 UUID 라 "찾을 수 없습니다"로 끝났을 뿐, **실제 UUID 였다면 로트 삭제·환전 완료가 그대로 실행**됐다.

**규칙**
1. `complete_fx_trade_with_fifo` / `reverse_completed_fx_trade` /
   `update_unconsumed_fx_lot` / `delete_unconsumed_fx_lot` — **탐지 목적 호출 금지.** 전부 쓰기 함수다.
2. 적용 여부는 **SELECT 로만** 확인한다(`restSelect('fx_lots',{limit:1})` 로 컬럼 확인).
   함수 존재까지 알아야 하면 **사용자에게 묻는다.**
3. 개발 브라우저에 관리자 세션이 있다고 **항상 가정**하라.

### 4.2 그 외 유지 규칙 (세션24 문서 §1 계속 유효)
- `src/lib/fxRegime.ts` 판정 로직 임의 변경 금지
- 백테스트는 `evaluateRegime(series.slice(0, i+1), ...)` 만 사용. 전용 판정 로직 금지
- 정책표 숫자 = **환전 후 남길 전사 외화 비중** (환전 비율 아님)
- 정책밴드 = **전 통화 외화 원화환산 합계 ÷ 전사 총자금** (특정 통화 비중 아님)
- 정기예금: 보유액·위험에는 포함, **환전 가능액·FIFO 후보에서는 만기 전 제외**
- 정기예금 이자는 환차손익 원가에 섞지 않음. 실제 입금 시 신규 로트
- 취득원가 이하 매도를 차단하지 않음. 손익은 표시하되 정책·결제버퍼가 우선
- 메디아나 월 3.0M USD 순유입 구조를 다른 법인에 일반화 금지
- 프로덕션 Supabase 는 SELECT 만. 변경은 사용자가 UI 버튼으로

## 8. Codex 재점검 및 마무리 (2026-08-12)

세션25 초안과 실제 코드를 다시 대조했다.

### 확인 완료

- MMDA/블랙리스트 가용성/5필드 중복키/교정 계획·실행 UI가 실제 코드에 존재한다.

- 프로덕션 쓰기 RPC는 탐지 목적으로 호출하지 않았다.

### 추가 수정

- CSV 등록: 검증 미리보기 뒤의 명시적 등록 버튼이 최종 승인 역할을 하도록 `window.confirm` 제거.
- 로트·과거 매각 삭제: 화면 내 대상 설명 → `삭제 실행/취소` 패널로 변경.
- 보유 로트 표에서 MMDA가 `보통예금`으로 잘못 표시되던 문제 수정.
- MMDA 연이율이 표에서 `—`로 숨겨지던 문제 수정.
- 정기예금 만기 검증 실패 전에 `saving=true`가 설정돼 버튼이 멈출 수 있던 문제 수정.
- 교정 설명의 과거 문구 `확인 창`을 실제 동작인 `미리보기 실행 버튼`으로 정정.
