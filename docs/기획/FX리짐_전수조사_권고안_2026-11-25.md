## 0. 먼저 읽을 것

### 0.1 이 문서를 쓰는 법

1. **§1 요약표**에서 전체 그림을 본다.
2. **§2 작업 순서**대로 진행한다. 의존 관계가 있으니 순서를 바꾸지 말 것.
3. 각 결함(§3)은 `증상 → 근거 → 원인 → 수정 지침 → 금지 → 완료 조건` 순서로 적었다.
   **완료 조건을 전부 만족해야 그 항목이 끝난 것이다.**
4. **§4 결정 필요 항목**은 사용자(재무팀장) 확인이 필요하다. 권장 기본값을 적어 두었으니,
   답을 받기 전에는 기본값으로 진행하되 커밋 메시지에 "결정 대기"를 명시한다.

### F-01 · P0 · 리짐 매각 지시가 엉뚱한 통화·수량으로 등록된다

### F-03 · P0 · 원장 대사가 정기예금 이동을 미반영 증감으로 잡는다

**증상**
- 외화 정기예금이 만기돼 보통예금으로 들어온 날, 외화거래명세 › 원장 탭의 **"자금일보 미반영 증감"에
  그 금액이 유입으로** 뜬다. `원장 반영`을 누르면 **같은 외화가 원장에 두 번** 존재하게 된다
  (정기예금 해지로 이미 보통예금 로트가 생겼는데 또 유입 로트를 만든다).
- 반대로 보통예금 → 정기예금 예치일에는 가짜 유출이 뜨고, 반영하면 FIFO 로트가 **실제로 소진**된다.
- 자금일보를 하루 건너뛴 날(공휴일 아님)은 이틀치 거래가 한 델타로 합쳐지는데, 원장은 하루치만 매칭해 가짜 미반영이 뜬다.

**근거**
- `src/hooks/useFxLedgerReconciliation.ts:78` — 델타 기준이 `daily.fx_{통화}` = **운전자금 외화만**.
- 같은 파일 104·109행 — 원장 매칭에서 `source_type = 'transfer'` 를 **통째로 제외**한다.
  그런데 원장(`fx_lots`)은 운전자금 + 정기예금을 모두 담는다.
- 같은 파일 80행 — `txnDate = rows[i - 1].date` 는 daily 행이 영업일마다 빠짐없이 있다고 가정한다.

**원인**
"같은 통화 안의 이동은 총액이 안 변하니 제외"라는 판단은 **원장 총액** 기준으로는 맞지만,
비교 대상인 `daily.fx_*` 는 **운전자금만**의 잔액이다. 운전 ↔ 정기예금 경계를 넘는 이동은
daily 관점에선 실제 증감이다.

**수정 지침**
1. 대사 계산을 순수 함수로 분리한다: `src/lib/fxReconcile.ts` 의 `computeReconcilePending(input)`.
   훅은 데이터 조회만 하고 이 함수를 호출한다. 테스트는 이 함수에 붙인다.
2. **원장 쪽 비교 기준을 "운전자금 계좌유형의 잔액 변화"로 바꾼다.**
   - 운전 계좌유형 = `demand_deposit`, `mmda` (정기예금 제외).
   - 날짜 d 의 원장 운전 순증 =
     `Σ(d 에 생긴 운전 계좌 로트의 original_amount) − Σ(d 의 소진 중 운전 계좌 로트에서 나간 amount)`.
   - 이렇게 하면 계좌 대체는 자동으로 처리된다: 정기예금 → 보통예금 대체는 "보통예금 로트 생성(+)",
     정기예금 로트 소진은 운전이 아니라 집계에서 빠진다. 별도 예외 규칙이 필요 없다.
   - ⚠ **로트 생성일 주의**: carryover 대체 로트는 FIFO 순서 보존을 위해 **원본의 취득일을 승계**한다.
     생성일로 `acquired_date` 를 쓰면 안 된다. `transfer_id` 가 있는 로트는
     `fx_lot_transfers.transfer_date` 를 생성일로 쓴다(`lib/fxLots.ts` 의 `interestStartDate` 와 같은 원리).
   - 개시 로트(`source_type='opening'`)는 거래가 아니라 스냅샷이므로 제외한다(현행 유지).
   - 이자 로트는 `account_type` 이 정기예금이면(재예치 복리) 운전 순증에서 자연히 빠진다.
3. **날짜 구간 매칭으로 바꾼다.** daily 행의 거래일을 `prevBizDay(row.date)` 로 두고,
   델타 i 는 `(prevBizDay(rows[i-1].date), prevBizDay(rows[i].date)]` 구간의 원장 운전 순증과 비교한다.
4. `원장 반영` 버튼이 만드는 로트·소진도 지금처럼 `source_type='daily_report_item'` 으로 남긴다(변경 없음).
5. **기존 오염 확인 (읽기 전용, 사용자에게 보고)** — `docs/db/fx_reconcile_duplicate_audit.sql`:
   정기예금 해지·대체가 있었던 날짜와 같은 날짜에 `daily_report_item` 유입 로트가 있는지 조회한다.
   ```sql
   select l.company, l.currency, l.acquired_date, l.original_amount, l.id
     from fx_lots l
    where l.source_type = 'daily_report_item'
      and exists (select 1 from fx_lot_transfers t
                   where t.company = l.company and t.currency = l.currency
                     and t.transfer_date = l.acquired_date       -- 같은 날 대체가 있었다
                     and (t.from_account_type = 'term_deposit' or t.to_account_type = 'term_deposit'))
    order by l.acquired_date desc;
   ```
   발견되면 **삭제하지 말고** 사용자에게 목록을 제시한다(되돌리기는 기존 `reverse_fx_consumption_by_source`·로트 수정 UI 로 사용자가 판단).

**금지**
- `source_type` 으로 예외를 하나씩 추가하는 방식으로 고치지 말 것 — 계좌유형 기준이 정답이다.
- 대체 로트의 생성일로 `acquired_date` 를 쓰지 말 것.

**완료 조건**

### F-04 · P0 · 소급 처분이 미래에 취득한 로트를 소진한다

**증상**
체결일·유출일·대체일을 과거로 입력하면(예: 오늘 8/20 인데 체결일 8/18), FIFO 가
**8/19 에 들어온 로트까지** 후보에 넣어 소진할 수 있다. 시간상 불가능한 처분이 장부에 남고
실현손익·잔존 장부환율이 틀어진다. `FxOrderProposeModal` 은 소급 등록을 명시적으로 지원하므로 실제로 발생 가능한 경로다.

**근거** (최신 정의 기준)
- `docs/db/fx_outflow_account_and_reverse.sql:146` (`complete_fx_trade_fill`) —
  후보 조건에 `acquired_date <= p_fill_date` 가 없다. 정기예금 만기만 본다.
- 같은 파일의 `consume_fx_lots_for_source` — 처분일 필터 없음.
- `docs/db/fx_term_deposit_investment_link.sql` (`transfer_fx_lots`) — 대체일 필터 없음.
- `src/lib/fxLots.ts` `previewFifoConsumption` — 클라이언트 미리보기도 같은 결함(서버와 일관되게 틀림).

**원인**
"그 시점에 존재했던 로트"라는 시간 조건이 빠졌다. 단, carryover 대체 로트는 원본 취득일을
승계하므로 `acquired_date` 만으로 필터하면 **대체 이전에는 존재하지 않던 로트**가 통과한다.

**수정 지침**
1. **`fx_lots.available_from date` 컬럼 추가** (= 그 로트가 장부에 생긴 날).
   - 대체로 생긴 로트: `fx_lot_transfers.transfer_date`.
   - 그 외: `acquired_date`.
   - backfill:
     ```sql
     update fx_lots l set available_from = t.transfer_date
       from fx_lot_transfers t where l.transfer_id = t.id and l.available_from is null;
     update fx_lots set available_from = acquired_date where available_from is null;
     alter table fx_lots alter column available_from set not null;
     ```
   - 신규 로트 생성 경로(모든 INSERT — `transfer_fx_lots`, `settle_fx_term_deposit` 의 이자 로트,
     클라이언트 `useFxLots` 의 유입 등록, CSV 임포트)에 `available_from` 을 채운다.
     기본값 트리거(`before insert ... new.available_from := coalesce(new.available_from, new.acquired_date)`)를 두면
     빠뜨린 경로도 안전하다. **대체 RPC 만은 반드시 명시적으로 transfer_date 를 넣을 것.**
2. 세 RPC 의 후보 조건에 `and available_from <= <처분일>` 추가:
   `complete_fx_trade_fill`(p_fill_date), `consume_fx_lots_for_source`(p_disposed_date), `transfer_fx_lots`(p_transfer_date).
   - 최신 본문을 그대로 복사해 한 줄만 추가한다. 시그니처를 바꾸지 않으므로 `create or replace` 로 충분하다.
   - 파일: `docs/db/fx_lot_available_from.sql` (컬럼 + backfill + 트리거 + 3개 RPC 재정의 + 검증 SELECT).
3. 클라이언트: `FxLot` 에 `availableFrom` 추가, `useFxLots` 매핑, `previewFifoConsumption` 필터에
   `(lot.availableFrom ?? lot.acquiredDate) <= asOfDate` 추가. **서버와 같은 규칙이어야 한다.**
4. **기존 위반 탐지 (읽기 전용, 사용자 보고)**:
   ```sql
   select c.company, c.currency, c.disposed_date, c.amount, l.available_from, c.source_type, c.source_id
     from fx_lot_consumptions c join fx_lots l on l.id = c.lot_id
    where l.available_from > c.disposed_date
    order by c.disposed_date desc;
   ```

**금지**
- `acquired_date <= 처분일` 만으로 고치지 말 것(대체 로트가 통과한다).
- 기존 위반 데이터를 스크립트로 자동 정정하지 말 것 — 목록 보고 후 사용자 판단.

**완료 조건**
- `fxLots.test.ts`: availableFrom 이 처분일보다 늦은 로트는 미리보기에서 제외된다.
- SQL 검증 SELECT 가 스크립트 끝에 있고, 적용 후 위반 목록 쿼리 결과가 사용자에게 보고됐다.
- 카탈로그로 적용 확인: `select prosrc like '%available_from%' from pg_proc where proname in (...)`.

### F-05 · P1 · 바구니 판정이 SSOT 훅 밖에 있다 (경보 이중계상)

### F-06 · P1 · 대표 통화 판정에 탭 통화 값이 섞인다

**증상**
EUR 탭을 보고 있으면 대표 통화(USD) 판정의 **결제버퍼 하한**이 EUR 결제버퍼로, 엔진 내부의
**예상 실현손익·원가 이하 여부**가 EUR 장부환율로 계산된다. 탭에 따라 결론이 달라질 수 있다
(지금은 버퍼 하한이 목표보다 낮아 결과가 같은 경우가 많을 뿐이다).

**근거**
- `src/pages/FxRegimePage.tsx:653` — `evaluateRegime(s, ctx, ...)` 의 `ctx` 는 현재 탭의 `useFxRegime` 결과.
- 주석 652행 "ctx(바구니 분모·보유액·정책밴드)는 통화와 무관하게 동일하다"는 **사실이 아니다**:
  `ctx.fxPayableKRW`(useFxRegime.ts:102)와 `ctx.avgAcquisitionRate`(85행)는 탭 통화 값이다.

**원인**
바구니 판정에 필요한 ctx 를 통화별 훅에서 빌려 썼다.

**수정 지침** (F-05 의 `buildBasketDecision` 안에서 처리)
1. 바구니 ctx 를 직접 구성한다:
   - `totalFundKRW = policyData.fxPolicyDenominator`
   - `fxHoldingKRW = policyData.fxPortfolioHoldings`
   - `fxPayableKRW = Σ_통화 payableFx(통화) × 정규화 종가(통화)` — **모든 통화 합계**.
     종가가 없는 통화는 시장환율(`useFx`)로 대체하고 그 사실을 결과에 표시.
   - `policyMin/MaxRatio = pctToRatio(fx_target_min/max)`
   - `avgAcquisitionRate = 대표 통화 FIFO 매도 예상 원가`(F-18 반영). 엔진 내부 손익은 보조 정보이고,
     최종 손익은 F-15 의 통화별 계산을 쓴다.
2. `FxRegimePage.tsx:652` 의 잘못된 주석을 삭제한다.

**완료 조건**
- 단위 테스트: 통화별 결제버퍼가 USD 2.5M · EUR 0.5M 일 때 `bufferFloorRatio` 가 두 통화 합계 기준.
- F-05 의 "탭 무관" 테스트로 함께 보장된다.

### F-07 · P1 · 백테스트가 실전 규칙과 다르다

**증상**
규칙 검증 탭의 결과(실현환율 프리미엄 등)가 실전과 다른 규칙으로 계산된다.
- 실전은 목표와 현재의 차이가 **리밸런싱 밴드(3%p) 이상일 때만** 거래한다.
- 백테스트는 점검일마다 **초과분을 전부** 판다.
- 실전의 분기 손실 한도도 백테스트에 없다.

결과적으로 **3%p 밴드 자체가 한 번도 검증된 적이 없고**, 2026-08-11 에 15~42% 목표 범위를 정한 근거 수치도
밴드 없는 규칙으로 계산된 것이다. (2026-11-25 담당자 문의 "목표 28.3% / 현재 29.4% 인데 조치 없음"이 바로 이 밴드의 효과다.)

**근거**
- `src/lib/fxBacktest.ts:251` — `requestedSellFx = Math.max(0, holdingFx - desiredHoldingFx)`, `actionRequired` 미참조.
- `grep -n "actionRequired\|rebalanceBand" src/lib/fxBacktest.ts` → 결과 없음.
- `fxRegime.ts` 머리말: "실시간 판정과 백테스트가 반드시 함께 사용 … 어떤 경우에도 분기하지 말 것".

**수정 지침**
1. 매도 조건에 `sig.decision.actionRequired` 를 반영한다. 매도량은 실전과 같게 `-suggestedTradeKRW / rate`
   (= 목표까지 내리는 양)로 하고, 결제버퍼·가용재고 상한은 현행 유지.
2. 입력 옵션 `ignoreRebalanceBand?: boolean` 을 추가해 **기존 결과와 비교**할 수 있게 한다(기본 false = 실전 규칙).
3. 분기 손실 한도를 선택 옵션으로 추가한다(`quarterLossCapKRW`). 분기 경계에서 사용량을 0으로 리셋.
4. `BacktestTab` 에 "실전 규칙 / 밴드 무시" 비교 표를 추가하고, 결과를 `fxRegime.ts` 의
   `DEFAULT_LEVEL_TARGETS` 주석 표(15~42% 근거)에 **재측정 값으로 갱신**한다. 결론이 바뀌면 사용자에게 보고.
5. 리밸런싱 밴드 1·2·3·4·5%p 민감도 표를 한 번 뽑아 `docs/기획/` 에 남긴다(정책회의 자료용).

**금지**
- 백테스트 전용 판정 함수를 만들지 말 것. `evaluateRegime` 결과를 그대로 쓰고, **집행 규칙만** 실전과 맞춘다.

**완료 조건**

대표 통화 장부환율로 계산한다. 실제로는 배분표대로 EUR·JPY 도 팔리므로 손익이 다르다.

**근거**
- `src/lib/fxVerdict.ts:189` `pnl = execFx × (rate − avgCostRate)`.

**수정 지침** (F-05 이후)
1. `buildBasketDecision` 에서 배분 행마다 해당 통화 가용 로트로 `previewFifoConsumption` 을 돌려
   통화별 예상 실현손익을 구하고 합계를 `verdict` 에 넘긴다(`VerdictInput.expectedPnlKRW`).
2. `buildVerdict` 는 넘겨받은 값으로 문구를 만든다(직접 계산하지 않음).
3. 조치 카드 배분표에 통화별 예상 손익 열 추가.

**완료 조건**
- 단위 테스트: USD 이익 + EUR 손실 배분 → 문구의 손익 = 두 통화 합.

---

### F-16 · P2 · 매도 가능량 상한이 대표 통화 재고만 본다

**증상**
대표 통화 가용재고가 정기예금 잠금으로 적으면, EUR 재고로 충분히 집행할 수 있어도 바구니 권고가 잘린다.

**근거**
- `src/pages/FxRegimePage.tsx:702` `requestedFx = min(suggestedKRW / rate, avail)` — `avail` 은 대표 통화만.

**수정 지침**
배분 행별로 `min(몫, 그 통화 가용재고 × 환율)` 을 적용하고, 부족분은 **다른 통화로 재배분하지 않는다**
(배분 규칙이 보유 구성비라 재배분하면 구성비가 왜곡된다). 대신 `shortfalls` 로 표시한다.
권고 총액(`requested`)과 집행 가능 총액(`executable`)을 둘 다 verdict 에 넘겨 문구에 반영한다.

**완료 조건**
- 단위 테스트: USD 가용 0 · EUR 가용 충분 → 집행 가능액 = EUR 몫, shortfall = USD 몫.

### F-17 · P3 · `useFxLots` 의 오늘이 UTC

**근거** `src/hooks/useFxLots.ts:435` `new Date().toISOString().slice(0, 10)`.
**영향** KST 00:00~09:00 에 오늘 만기 정기예금이 잠긴 것으로 계산된다.
**수정** `todayStr()`(lib/bizDay) 로 교체. 같은 패턴을 `grep -rn "toISOString().slice(0, 10)" src` 로 찾아
FX 관련 파일만 함께 교체(다른 도메인은 이번 범위 밖 — 목록만 보고).

### F-18 · P2 · 판정용 장부환율이 매도 대상과 다르다

**증상** 조치 카드·손실 한도가 쓰는 장부환율은 **잠긴 정기예금까지 포함한 전체 잔존 로트 가중평균**이다.
실제 매도는 가용 로트를 FIFO 순으로 소진하므로 원가가 다르다.
**근거** `src/hooks/useFxLots.ts:444` `bookRate: weightedBookRate(lots)`.
**수정** `useFxLots` 에 `availableBookRate`(가용 로트만 가중평균)를 추가하고, 판정·예산은 F-08/F-15 의 FIFO 미리보기를 쓴다.
화면의 "잔존 장부환율" 표시는 기존 `bookRate` 를 유지하되 라벨을 `전체 잔존 장부환율`로 명확히 한다.
