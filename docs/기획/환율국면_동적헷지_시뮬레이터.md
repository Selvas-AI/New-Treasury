>    "환율이 오르니 더 산다"가 성립하지 않는다.

> 하락 국면 매도만 남긴 **비대칭 프로토콜**이 더 나을 것. 밴드 적용본(제한적)이
> 무제한본보다 3.2억 우수했다는 사실이 이 방향을 지지한다. 프로토콜 탭에서 값만 바꿔 재검증 가능.

>
> ### 구현 중 확정된 설계 변경 (근거 문서와 다른 부분)
> 1. **ADX·ATR → Efficiency Ratio·변동성 Z-Score** — ECOS 는 종가만 제공(고가/저가 없음)해 원안대로 계산 불가.
> 2. **칼만 필터는 JS 로 구현** — 1차원이라 행렬 연산 불필요(약 20줄). Python 백엔드 불필요.
> 3. **평활가/원시가 용도 분리** — 추세 지표만 평활가, 변동성·볼린저는 원시 종가.
>    평활가로 변동성을 재면 정의상 과소평가된다(실측 1.11% vs 실제 5.72%).
> 4. **칼만 q=0.5→2** — 근거 문서 예시값은 원/달러 가격대에서 약 4영업일 지연을 만든다(실측 14.8원).
> 5. **추세 크기 게이트 `minTrendMovePct` 신설(1.5%)** — ER 은 스케일 불변이라 미세 드리프트를
>    강한 추세로 오분류한다. 20영업일 랜덤워크 1σ(≈2%)의 3/4 로 설정.
>
> ### 운영상 확인된 제약
> - **PostgREST `max-rows=1000`** — 5년치(1,129건) 조회 시 조용히 잘린다. keyset 페이지네이션 적용.
> - **ECOS 1회 500건 상한** — 백필·일일보충 모두 연 단위로 끊어 호출해야 한다.
> - **GAS 연속 호출 간헐 실패** — "사용할 수 없는 주소" 예외. 연도별 3회 재시도 + 5초 간격으로 대응.
>   한 해가 실패해도 배치 전체를 중단하지 않는다(upsert 라 재실행 안전).
> 배포 방침: **1단계 로컬 전용**(DEV 게이트). 검증 후 커밋/푸시/배포.

## 1. 입력 자료 대조 — 프롬프트 vs 실제 구조

프롬프트는 잘 쓰였지만 **다른 아키텍처를 가정하고 있다.** 그대로 구현하면 동작하지 않는다.

| 프롬프트 전제 | 이 프로젝트의 실제 | 조치 |
|---|---|---|
| "기존 백엔드에서 `/api/fx-rates` 엔드포인트 구축" | **백엔드 서버 없음.** GitHub Pages 정적 배포 + Supabase(PostgREST) + GAS Web App | Supabase 테이블 `fx_rate_history` + `restSelect()` 조회로 대체. GAS는 수집기로만 사용 |
| "React `.jsx`" | 프로젝트 전체가 **TypeScript**. `.jsx` 파일 0개 | `.tsx`로 작성. 기존 타입(`FxCode` 등) 재사용 |
| "최근 3~6개월 시계열을 fetch" | **환율 이력이 존재하지 않음.** `useFx`는 GAS에서 당일 스냅샷만 받아 4분 캐시 | 선결 과제 — §3 |
| "Tailwind CSS로 모던 UI" | ✅ Tailwind v4 사용 중 | 그대로. 단 **다크모드 필수**(앱 전역 지원) |
| "useEffect로 fetch, 로딩·에러 처리" | ✅ 프로젝트 표준과 일치 | 그대로. 단 훅 반환값 **메모이즈 필수**(무한루프 전례) |
| SMA20 + 볼린저 밴드만 사용 | — | Google Doc이 요구하는 EMA/MACD/ADX/ATR/칼만이 더 정교. §4에서 통합 |

**프롬프트와 Google Doc의 관계**: 프롬프트는 Doc의 **가장 얕은 층(2.2 볼린저)** 만 구현한다. Doc은 여기에 추세 지표(2.1), 노이즈 제거(3.2 칼만), 확률 추론(3.1 MSM)을 얹는다. 둘은 경쟁 관계가 아니라 **난이도 계층**이므로, 계층별로 나눠 쌓는다.

## 3. Phase 1 — 환율 시계열 확보 (선결 · 최우선)

**이게 없으면 뒤의 모든 것이 0이다.** 그리고 이건 되돌릴 수 없는 종류의 지연이다 — 오늘 수집을 시작하지 않으면 내일의 데이터도 영영 없다.

### 3.1 데이터 출처: ECOS 한 곳

Google Doc은 5개 소스를 비교하지만, **우리 상황에서는 ECOS 단일 소스가 정답이다.**

- 이미 GAS에 연동돼 있고 (`?type=fxstddev`), 한국은행 공식 통계라 회계 기준과 일치
- **일별 이력을 과거로 소급 조회할 수 있다** → 과거 3년치를 하루 만에 백필 가능
- 무료. Yahoo/Alpha Vantage는 SLA 없거나 호출 제한이 빡빡함
- ⚠ Doc이 권하는 15분봉 인트라데이는 **우리에겐 불필요.** 기업 자금 의사결정 주기는 일 단위이고, 인트라데이를 넣으면 GAS 할당량 사고(세션17차)가 재발한다

### 3.2 ⚠ GAS 코드 수정 필요 — 날짜가 버려지고 있음

`Code.gs:1005-1007` `fetchEcosRates_()`가 **값만 반환하고 `TIME`(날짜)을 버린다.**

```javascript
return rows
  .map(function(r) { return parseFloat(r.DATA_VALUE); })   // ← r.TIME 유실
  .filter(function(v) { return !isNaN(v) && v > 0; });
```

표준편차 계산에는 날짜가 필요 없어서 문제가 없었지만, **시계열 저장에는 날짜가 필수**다. `{ date, rate }` 배열을 반환하도록 수정하고, 신규 라우트 `?type=fxhistory&from=&to=&currency=`를 추가한다.
→ **GAS 재배포 필요.**

### 3.3 신규 테이블 `fx_rate_history`

```sql
create table if not exists public.fx_rate_history (
  id          uuid primary key default gen_random_uuid(),
  currency    text not null,          -- USD | EUR | JPY | GBP | CNY
  rate_date   date not null,
  rate        numeric not null,       -- 1외화 = N원 (JPY는 100엔 기준 주의)
  source      text not null default 'ecos',
  created_at  timestamptz default now(),
  unique (currency, rate_date)
);
create index on public.fx_rate_history (currency, rate_date desc);
```

- 법인 무관 **전사 공용** (환율은 회사별로 다르지 않다) → `company` 컬럼 없음
- `unique(currency, rate_date)` → 재수집 시 upsert로 멱등
- RLS는 기존 테이블과 동일한 permissive 정책

### 3.4 수집 방식: 수동 백필 + 일 1회 자동

| 단계 | 방법 | 비고 |
|---|---|---|
| 초기 백필 | 관리자 화면 "환율 이력 수집" 버튼 → 연도별 순차 호출 | ECOS 1회 500건 한도 → **연 단위로 쪼개서 호출**. 통화당 3년 = 3회 |
| 일일 갱신 | 앱 진입 시 "마지막 저장일 < 전영업일"이면 1회만 보충 | Tier1 자동갱신과 동일한 "오늘 이미 했으면 skip" 패턴 재사용 |

⚠ **폴링 금지.** `isGasBlocked()` 서킷브레이커를 반드시 통과시키고, 차단 중이면 조용히 skip한다.

### 3.5 ⛔ 선행 조치 — ECOS_API_KEY 로테이션

세션20차에 **실제 키가 브라우저 화면에 노출**됐다. 코드 마스킹은 반영됐지만 키 자체는 아직 살아 있다. 이 Phase는 ECOS 호출량을 크게 늘리므로, **착수 전 키 재발급 필수.**

## 4. Phase 2 — 국면 판정 엔진 (`src/lib/fxRegime.ts`)

순수 함수 모듈. React 의존성 0. **테스트 가능하고 시뮬레이터가 그대로 재사용한다** — 이게 백테스트와 실시간 판정이 절대 어긋나지 않게 하는 유일한 방법이다.

### 4.1 계층별 구현 범위

| 계층 | 지표 | JS 구현 | 채택 |
|---|---|:--:|---|
| **T1 기본** | SMA20, 볼린저(±2σ), 표준편차 | 쉬움 | ✅ Phase 2 |
| **T2 추세** | EMA(20/60/120), MACD(12/26/9), ADX(14) | 보통 | ✅ Phase 2 |
| **T3 변동성** | ATR(20), 연환산 변동성 Z-Score(252일) | 보통 | ✅ Phase 2 |
| **T4 평활** | **칼만 필터 (1차원 스칼라)** | 약 20줄 | ✅ Phase 2 |
| **T5 확률** | 마르코프 국면전환(MSM) 평활확률 | **JS 부적합** | ⏸ 보류 — §7 |

**칼만 필터가 JS로 된다는 점이 중요하다.** Doc은 `pykalman`을 전제하지만, 관측 1차원·상태 1차원 랜덤워크 모델이면 행렬 연산이 필요 없다:

```
predict:  x⁻ = x,  P⁻ = P + Q
update:   K  = P⁻ / (P⁻ + R)
          x  = x⁻ + K(z − x⁻)
          P  = (1 − K) P⁻
```
Q(전이 노이즈)/R(관측 노이즈) 비율만 조정하면 평활 강도가 결정된다. Doc의 `Q=0.5, R=10.0`을 초기값으로 쓰고 **탭3 시뮬레이터에서 튜닝**한다.

⚠ 지표는 **칼만 평활가 기준으로 계산**하되, 국면 표시 옆에 원시 종가를 항상 병기한다. 평활가만 보여주면 실무자가 "내가 아는 환율과 다르다"고 신뢰를 잃는다.

### 4.2 5×2 국면 매트릭스 (Doc §2.3 준용)

| 코드 | 국면 | 판정 조건 |
|---|---|---|
| ① | 강한 상승 | EMA 정배열 + MACD>Signal + ADX>30 |
| ② | 온건 상승 | EMA20>60 + ADX 20~30 |
| ③ | 횡보 | ADX<20 |
| ④ | 온건 하락 | EMA20<60 + ADX 20~30 |
| ⑤ | 강한 하락 | EMA 역배열 + MACD<Signal + ADX>30 |
| A | 고변동성 | ATR > 60일평균×150% 또는 Vol Z > 1.5 |
| B | 저변동성 | 그 외 |

**히스테리시스 필수** — Doc이 지적한 웝소(whipsaw) 방지. 국면 전환은 **2영업일 연속 동일 판정**에서만 확정한다. 이 규칙 하나가 무의미한 매매 지시 남발을 막는다.

### 4.3 ⭐ 우리 회사 고유 제약 — 프롬프트가 옳게 지적한 부분

프롬프트의 "**최소 원화/외화 버퍼 제약을 주석으로 명시**" 요구는 정확하며, 오히려 주석이 아니라 **코드로 강제**해야 한다. 우리는 수출기업이 아니라 **외화 순지출 구조**(수입 결제)이므로 Doc의 수출기업 전제를 그대로 쓰면 방향이 반대가 된다.

```
최종 목표비율 = clamp(국면별 목표비율,
                     하한 = 향후 N개월 외화 결제예정액 / 가용자금총액,
                     상한 = policy_params.fx_target_max)
```

- **하한**: 이만큼은 국면과 무관하게 반드시 보유. 없으면 결제일에 고가로 되사야 함
  → `cashflow_plan_items`의 외화 출금 계획을 재사용 (신규 입력 없음)
- **상한**: 기존 FX Target Band. **국면 엔진이 정책 밴드를 넘어설 수 없다**
- 알고리즘 제안이 밴드와 충돌하면 **정책이 이긴다.** 화면에 충돌 사실을 명시하고 의결을 요구한다

### 4.4 출력 스키마

Doc §4.2 JSON을 채택하되 우리 필드를 추가한다.

```ts
interface FxRegimeSignal {
  asOf: string
  currency: FxCode
  market: { rawClose: number; kalmanClose: number }
  signals: { adx: number; macdHist: number; volZScore: number; atrPct: number
             sma20: number; bbUpper: number; bbLower: number }
  regime: { code: string; label: string; trendStrength: number; confirmedDays: number }
  decision: {
    targetFxRatio: number          // 국면 원안
    appliedFxRatio: number         // 버퍼·밴드 클램프 후 (실제 사용값)
    clampedBy: 'none'|'buffer'|'policy_band'
    currentFxRatio: number
    suggestedTradeFx: number       // + 매수 / − 매도
    action: string
    rebalanceFrequency: string
  }
}
```

## 5. Phase 3 — 정책 프로토콜 (탭2)

국면별 목표 비율을 **하드코딩하지 않는다.** 회사마다 다르고, 정책회의 의결 대상이기 때문이다.

- 저장: `policy_params` 재사용 — `fx_regime_target_1a` … `fx_regime_target_5b` (10개 키) + `fx_regime_buffer_months` / `fx_regime_hysteresis_days` / `fx_regime_kalman_q` / `fx_regime_kalman_r`
- **신규 테이블 불필요.** `usePolicyParams` 훅 그대로 사용
- 편집 권한은 기존 `canAction('policy','write')` 게이트
- 프로토콜 변경은 **의결사항으로 남긴다** — `policy_decisions`에 연결하여 "언제 누가 규칙을 바꿨는지" 추적

기본값(Doc §4.1 기반, 외화 순지출 구조로 보정):

| 국면 | 목표 외화비중 | 근거 |
|---|---|---|
| ①-A 강한상승/고변동 | 상한 유지 | 환차익 구간, 매도 지연(Lagging) |
| ②-B 온건상승/저변동 | 상한 −5%p | 점진 축소 |
| ③ 횡보 | 정책 중립값 | 벤치마크 유지 |
| ④ 온건하락 | 하한 +10%p | 축소 개시 |
| ⑤-B 강한하락/저변동 | **하한** | 고착 하락 — 즉시 최대 매도 |
| ⑤-A 강한하락/고변동 | 하한 +5%p | 급락 중 패닉셀 방지, 분할 |

## 6. Phase 4 — 시뮬레이터 (탭3) ★ 핵심 산출물

### 6.1 백테스트 엔진

```
for (각 영업일 d in 기간) {
  window = history[..d]                    // ⚠ look-ahead 절대 금지
  signal = evaluateRegime(window, protocol) // Phase 2 엔진 그대로
  if (리밸런싱일 && |목표−현재| > 임계치) 거래 실행 (수수료·스프레드 반영)
  자산가치 기록
}
```

⚠ **`fxRegime.ts`를 그대로 호출해야 한다.** 시뮬레이터용 로직을 따로 만들면 "백테스트는 좋았는데 실전은 다르다"가 되고 아무도 믿지 않게 된다.

### 6.2 성과 지표

- 기간말 원화 환산 자산가치 / 아무것도 안 한 경우(Buy&Hold) 대비 초과분
- 최대 낙폭(MDD), 거래 횟수, 누적 거래비용
- **실현 환차손익 합계** — FIFO 원장 기획과 정합
- ⭐ **"7월에 이 프로토콜을 썼다면?"** — 실제 사고 구간 리플레이. 이게 경영진 설득의 유일한 근거가 된다

### 6.3 비교 모드

프로토콜 A / B / Buy&Hold를 **동일 기간에 동시 실행**하여 한 차트에 중첩. 단일 결과만 보여주면 "좋아 보인다"밖에 판단할 수 없다.

## 7. 보류 결정 — MSM (마르코프 국면전환)

Doc이 가장 강조하는 기법이지만 **1차 범위에서 제외한다.**

- `statsmodels.MarkovRegression`은 EM 알고리즘 반복 적합이 필요. JS 포팅은 수백 줄이며 수렴 실패 처리가 까다롭다 (Doc의 예시 코드조차 `except`로 균등확률 폴백)
- Python 배치 서버를 세우면 **이 앱의 무서버 아키텍처가 깨진다** — 운영 부담이 기능 가치를 초과
- ADX + 히스테리시스 + 칼만 조합으로 **웝소 방지라는 실질 목적은 이미 달성**된다. MSM이 추가로 주는 것은 "확신도 %" 표시인데, 이는 있으면 좋은 정보이지 의사결정을 바꾸는 정보가 아니다

**재검토 조건**: 탭3 백테스트에서 규칙 기반 판정의 오탐이 유의하게 많다고 정량 확인되면 그때 착수한다. 그 전에는 근거 없는 복잡도다.

## 10. 결정 필요 사항

착수 전 확인이 필요한 5가지.

1. **통화 범위** — USD만? 아니면 5종 전체? (권장: **USD만** 시작. 국면 판정 가치가 USD에 집중되고 ECOS 호출도 1/5)
2. **백필 기간** — 3년 / 5년? (권장: **5년** — 2022년 급등장을 포함해야 고변동 국면 샘플이 생김)
3. **Phase 1 선배포 여부** — 수집만 먼저 프로덕션에 올릴지 (권장: **예**. 데이터 공백은 소급 불가)
4. **버퍼 산정 기준** — 향후 몇 개월치 외화 결제예정액을 하한으로 볼지 (권장: **3개월**)
5. **착수 범위** — Phase 0–1만 먼저 할지, 0–5 일괄 진행할지
