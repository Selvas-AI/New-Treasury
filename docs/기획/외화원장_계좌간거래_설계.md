# 외화 원장 — 계좌 간 거래·정기예금 라이프사이클 설계

> 작성: 2026-08-20 (세션26차 11일차 후속)
> 배경: 외화가 나가는 케이스가 "원화로 매각" 하나만 구현돼 있어, 매입대금 결제·
> 계좌 대체·정기예금 예치/해지/재예치가 원장에 반영되지 않는다는 리포트.

## 1. 현재 구현 상태 (실측)

### 1.1 원장이 아는 거래

| 방향 | `source_type` | 발생 경로 | FIFO 소진 | 실현손익 |
|---|---|---|---|---|
| 유입 | `opening` | 개시 로트 등록 / CSV 임포트 | — | — |
| 유입 | `daily_report_item` | 자금일보 잔액 증가분 반영 | — | — |
| 유입 | `manual` | 데이터 등록 › 외화 유입 등록 | — | — |
| 유출 | `fx_trade_history` | 매각 체결(부분 체결 포함) | O | O |
| 유출 | `daily_report_item` | 자금일보 잔액 감소분 반영 | O | O |
| 유출 | `manual` | 데이터 등록 › 외화 유출 등록 | O | O |

`fx_lots.source_type` CHECK 제약: `('opening','daily_report_item','manual','adjustment')`
— **`transfer`·`interest`·`investment` 없음.**

### 1.2 지원되지 않는 것

| # | 케이스 | 현재 | 문제 |
|---|---|---|---|
| ① | 매입대금 결제 등 대외 지급 | 수동/자금일보 유출로 **기록은 가능** | 매각과 구분이 안 됨. 환차손익 요약에 "매각 실적"으로 섞임 |
| ② | 보통예금 ↔ MMDA 계좌 대체 | **불가** | 총액이 안 변하는 거래를 표현할 방법이 없음 |
| ③ | 보통예금/MMDA → 정기예금 예치 | 로트 `수정`으로 계좌유형 변경만 가능 | **일부 금액만 예치 불가**(로트를 쪼갤 수 없음) · 이력 미기록 · 과거 사실 왜곡 |
| ④ | 정기예금 만기 해지 | **불가** | 해지하면 term_deposit 로트가 보통예금으로 바뀌어야 하는데 경로 없음 |
| ⑤ | 해지 후 재예치 | **불가** | 새 만기일·계좌유형을 가진 로트로 이어갈 방법 없음 |
| ⑥ | 이자 수취 | 수동 유입으로 등록 가능 | 원금과 구분 안 됨(`expectedTermInterestFx` 는 예상치일 뿐) |
| ⑦ | 운용자금(`investments`) ↔ 원장 연동 | **전혀 없음** | 아래 실측 참조 |

### 1.3 ⑦의 실측 증거 (메디아나 USD)

`investments` 의 외화 정기예금 3건:

| 상품 | 은행 | 금액 | 개시 | 만기 | active |
|---|---|---|---|---|---|
| 정기예금 | 국민은행(외화) | 5,000,000 | 2026-06-17 | 2026-09-17 | true |
| 정기예금 | 기업은행(외화) | 5,000,000 | 2026-03-17 | 2026-06-17 | **false (해지됨)** |
| 정기예금 | 국민은행(외화) | 1,000,000 | 2026-03-11 | 2026-09-11 | true |

원장의 `term_deposit` 로트 2건(2026-06-17 만기 09-17 / 2026-03-11 만기 09-11)과 금액·
만기가 일치하지만 **서로를 참조하는 컬럼이 없다.** 그리고 2026-03-17 건은 이미 해지됐는데
원장에는 해지 흔적이 없다 — 두 장부가 우연히 맞아 보일 뿐 **연결돼 있지 않다.**

## 2. 설계 원칙

### 2-1. 내부 대체 = 원자적 [FIFO 소진 + 원가승계 신규 로트] 쌍 ⭐

계좌 간 이동은 **환전이 아니다.** 외화가 외부로 나간 것도, 새로 들어온 것도 아니다.
따라서:

- **총 외화 잔액 불변**
- **실현손익 0** — 장부환율(취득원가)을 그대로 물려받는다
- **FIFO 순서 보존** — 취득일(`acquired_date`)도 승계한다

핵심은 **소진된 로트별로 새 로트를 1:1로 만드는 것**이다. 하나로 뭉치면 장부환율이
가중평균으로 뭉개져 원가 정보가 소실된다.

```
[대체 전] 보통예금 로트A 600,000 @1,400 (취득 2026-01-08)
          보통예금 로트B 400,000 @1,450 (취득 2026-02-20)

USD 1,000,000 을 정기예금으로 예치 (2026-08-20, 만기 2026-11-20)

[대체 후] 로트A 잔액 0        ← consumption 600,000 (source_type='transfer')
          로트B 잔액 0        ← consumption 400,000 (source_type='transfer')
          정기예금 로트C 600,000 @1,400 (취득일 2026-01-08 승계, 만기 2026-11-20)
          정기예금 로트D 400,000 @1,450 (취득일 2026-02-20 승계, 만기 2026-11-20)

총액 1,000,000 유지 · 실현손익 0 · 이후 FIFO 순서도 원래대로
```

#### 평가 방식은 법인별 정책으로 선택한다 (2026-08-20 결정)

은행 실무가 회사마다 다르므로 `policy_params.fx_transfer_valuation` 으로 고른다
(FIFO 계좌유형 우선순위와 같은 거버넌스 — 정책회의만 편집).

| | `carryover` (원가승계, **기본값**) | `revalue` (재평가) |
|---|---|---|
| 신규 로트 수 | 소진된 로트 수만큼 **1:1** | **1건** (환율이 하나로 통일되므로) |
| 장부환율 | 원본 승계 | 대체환율 |
| 취득일 | 원본 승계 → **FIFO 순서 보존** | 대체일 (새 취득으로 본다) |
| 실현손익 | **0** | (대체환율 − 장부환율) × 금액 |
| 대체환율 입력 | 불필요 | **필수** |

> ⚠ 재평가는 사실상 **매각 + 재매입**이라 실현손익이 발생하고 원가 이력이 리셋된다.
> 그래서 두 가지를 강제한다:
>   1. 각 대체 건에 **그때 적용한 방식을 기록**한다(`fx_lot_transfers.valuation_method`).
>      정책이 나중에 바뀌어도 과거 이력의 해석이 흔들리지 않아야 한다.
>   2. 화면에서 방식별로 예상 결과(손익 0 vs 실현손익 N)를 **저장 전에 보여준다.**

### 2-2. 거래 유형(`txn_type`)을 `source_type` 과 분리

지금은 `source_type` 하나가 "어느 화면에서 만들었나"와 "무슨 거래인가"를 겸한다.
매입대금 결제가 매각과 똑같이 기록되는 원인이다. 둘을 나눈다.

| `txn_type` | 방향 | 실현손익 | 설명 |
|---|---|---|---|
| `sale` | 유출 | **O** | 원화로 환전(매각). 환차손익 요약의 정본 |
| `payment` | 유출 | **O** | 매입대금·수수료 등 대외 외화 지급. 손익은 나지만 매각 실적은 아님 |
| `transfer_out` / `transfer_in` | 내부 | **0** | 계좌 대체(예치·해지·계좌간 이체). 짝으로만 존재 |
| `interest` | 유입 | — | 이자 수취. 수취일 환율의 **신규 로트** |
| `acquisition` | 유입 | — | 수출대금 회수 등 외화 수취 |
| `opening` | 유입 | — | 개시 재고 |

- `fx_lot_consumptions.txn_type` / `fx_lots.txn_type` 추가(기존 행은 backfill:
  `fx_trade_history`→`sale`, `manual`/`daily_report_item` 유출→`payment`, 유입→`acquisition`).
- **환차손익 요약**은 `sale` 만 집계하고 `payment` 는 별도 줄로 분리한다
  (지금은 섞여 "매각 실적"이 부풀려진다).

### 2-3. 정기예금은 `investments` 가 원장(原帳), `fx_lots` 가 재고

정기예금은 **두 장부에 동시에 존재**한다. 어느 쪽이 정본인지 정해야 한다.

| 정보 | 정본 |
|---|---|
| 계약 조건(은행·금리·만기·상품명), 만기 처리 여부 | `investments` |
| 외화 원가(장부환율)·FIFO 순서·환전 가능 여부 | `fx_lots` |

→ **`fx_lots.source_type='investment'`, `source_id=investments.id`** 로 연결한다.
`fx_lots` 에 이미 `(company, currency, source_type, source_id)` unique 제약이 있어
한 예금이 두 번 반영되는 것도 DB가 막아준다.

> ⚠ 단, 2-1 원칙상 예치 1건이 **여러 로트로 쪼개질 수 있다**(원가승계). unique 제약과
> 충돌하므로 `source_id` 를 예치 단위가 아니라 **대체 이벤트 id**(`fx_lot_transfers.id`)로
> 두고, `investments.id` 는 별도 컬럼(`investment_id`)으로 참조하는 편이 맞다.

## 3. 구현안

### Phase 1 — 계좌 간 대체 (②③⑤ 해결)

**DB** `docs/db/fx_lot_transfer.sql`
- `fx_lots.source_type` CHECK 에 `'transfer'`, `'interest'`, `'investment'` 추가
- `fx_lots.txn_type` / `fx_lot_consumptions.txn_type` 컬럼 추가 + 기존 행 backfill
- `fx_lots.investment_id uuid null` (운용자금 연결용)
- 신규 테이블 `fx_lot_transfers` — 대체 이벤트 헤더
  `(id, company, currency, transfer_date, from_account_type, to_account_type,
    amount, maturity_date, annual_interest_rate, investment_id, memo, created_by)`
- 신규 RPC `transfer_fx_lots(...)` — **한 트랜잭션 안에서**
  1. `from_account_type` 로트만 대상으로 FIFO 소진(정책 우선순위 적용, 정기예금 만기 검사)
  2. 소진된 로트마다 신규 로트 생성(장부환율·취득일 승계, `to_account_type`)
  3. `fx_lot_transfers` 헤더 1건 기록
  - 실현손익은 항상 0 으로 기록(`disposal_rate = acq_rate`)
- 원복 RPC `reverse_fx_lot_transfer(transfer_id)` — 신규 로트 삭제 + 원본 잔액 복원.
  ⚠ 신규 로트가 이미 일부 소진됐으면 거부한다.

**UI** 외화거래명세 › 데이터 등록 탭에 `🔄 계좌 간 대체` 카드
- 대체일 / 출금 계좌유형 / 입금 계좌유형 / 금액 / (정기예금이면) 만기일·연이율 / 메모
- 저장 전 **원가승계 미리보기**: 어느 로트에서 얼마가 빠져 어떤 장부환율로 넘어가는지
- 원장 탭에서는 대체 유입 로트에 `대체` 배지 + 원천 로트 링크

### Phase 2 — 정기예금 라이프사이클 + 운용자금 연동 (④⑦ 해결)

**예치**: 운용자금(`InvestPage`)에서 외화 정기예금을 신규 등록하면 원장 반영을 제안
→ Phase 1 의 대체(보통예금/MMDA → 정기예금)를 `investment_id` 를 달아 실행.

**해지(만기/중도)**: 운용자금에서 `만기처리`(`setActive(false)`) 시 원장 반영 팝업
1. **원금**: 정기예금 → 보통예금 또는 MMDA 대체(원가승계, 손익 0)
2. **이자**: 수취 금액 입력 → **해지일 환율의 신규 로트**(`txn_type='interest'`)
   - 이자는 새로 생긴 외화이므로 원가승계 대상이 아니다. 승계하면 원가가 왜곡된다.
3. **재예치**: "해지 후 바로 재예치" 체크 시 ①을 정기예금 → 정기예금 대체로 바꾸고
   새 만기일·금리를 받는다(원가·취득일은 여전히 승계).

**정합성 점검 패널**: 원장의 `term_deposit` 잔액 합계 vs `investments` 의 외화
정기예금 `active=true` 합계를 비교해 불일치를 경고. 1.3 의 "따로 노는 두 장부"가
다시 벌어지지 않게 하는 안전장치.

### Phase 3 — 거래 유형 정착 (①⑥ 해결)

- 수동 유출 등록 폼에 거래 유형 선택(`매각` / `대외 지급`) 추가
- 자금일보 반영 시에도 항목 카테고리로 유형 추정(`trade_ap_payment` → `payment` 등)
- 환차손익 요약을 `매각 실현손익` / `지급 실현손익` / `미실현` 3줄로 분리
- 원장 처분 내역의 `경로` 열에 거래 유형 배지 표시

## 5. 우선순위 제안

1. **Phase 1** — 계좌 간 대체. 지금 아예 표현 불가능한 거래라 가장 시급하다.
2. **Phase 3** — 거래 유형. DB 변경이 작고, 환차손익 요약의 정확도를 바로 올린다.
3. **Phase 2** — 운용자금 연동. 두 화면·두 테이블을 엮어야 해 범위가 가장 크다.
   Phase 1 의 대체 RPC 가 있어야 성립하므로 순서상으로도 뒤다.
