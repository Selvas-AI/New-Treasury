> 작성: 2026-08-14 (세션26차)
> 배경: 2026-08-14 정책회의에서 **FX 리짐 모델을 FX 정책 모델로 채택**.
> 선행 문서: `환율국면_인수인계_세션24.md`, `환율국면_인수인계_세션25.md`

## 0. 한 줄 요약

FX 리짐(`/fx-regime`)은 **실무 일상 화면으로 분리 유지**하고, 그 화면이 쓰는
**정책 기준값 전부를 자금정책 관리(`/policy` › FX 정책)로 이관**한다.
실무자는 정책 기준을 볼 수만 있고 바꿀 수 없다.

---

## 1. 두 모델의 관계 — 대체가 아니라 계층

| | 기존 FX 정책 탭 (`FxPolicyTab.tsx`) | FX 리짐 (`FxRegimePage.tsx`) |
|---|---|---|
| 산출물 | **한도**: 최대변동폭(σ×비중×Z) → 허용손실÷변동폭 = 한도A, 총자금×`fx_max_fx_ratio` = 한도B, 실효한도 = min → 권고 밴드 | **시점·금액**: 앵커 대비 수준(5) × 추세(3) → 목표 잔존비중 → 버퍼·밴드 clamp → 권고 환전액 |
| 성격 | 정적, 분기 의결 | 동적, 매일 |
| 집행 | 초과분 매도 발의 → 승인 → 완료 (`fx_trade_history`) | 권고만 생성, 집행은 동일 워크플로우 재사용 |
| 저장소 | `policy_params` | `policy_params` (`fx_regime_*` / `fx_level_*`) |

리짐 엔진은 이미 `policyMinRatio` / `policyMaxRatio` 를 clamp 입력으로 받도록
설계되어 있다(`fxRegime.ts` `TreasuryContext`). 그 밴드를 만들어내는 것이 기존
손실허용 한도 모델이다. 따라서 다음 계층으로 확정한다.

> **한도(밴드)는 리스크 모델이, 시점과 금액은 리짐이 정한다.**

기존 σ×Z 모델은 폐기하지 않고 **한도 계산기**로 존치하되, 계산 결과를 자동
저장하지 않고 `📥 정책 밴드로 불러오기` 를 눌러야 의결 초안에 반영되도록 바꾼다.

## 2. 소유권 원칙 — 가정은 정책, 사실은 실무

사용자 결정(2026-08-14): **실무자가 독단으로 바꾸는 일은 없어야 한다.**

| 구분 | 항목 | 편집 주체 |
|---|---|---|
| **정책 소유**<br>(실무 화면 편집 불가) | 정책 밴드 상·하한, 앵커, 수준 임계 4개, 5×3 목표 잔존비중, 국면 판정 4개, 확정일수, 리밸런싱 밴드, 강제환전 기한, **월 외화 유입 가정**, **결제 버퍼**, 분기 손실실현 한도 | 정책회의 (`/policy`) |
| **실무 입력**<br>(사실 기록) | 이번 분기 실현손실 실적, 매각 체결환율, FIFO 로트 등록·CSV 이관 | 실무자 (`/fx-regime`, `/fx-ledger`) |
| **자동 조회**<br>(아무도 편집 불가) | 총자금, 전사 외화 바구니, 통화별 보유액, FIFO 장부환율, ECOS 환율 이력 | Treasury / ECOS |

**월 유입액·결제 버퍼를 정책 소유로 둔 이유**: 이 둘은 버퍼 하한을 통해 권고
환전액을 직접 움직인다. 결제 버퍼를 250만불 → 500만불로 올리면 하한이 올라가
"환전 불필요" 가 나온다. 실무자가 손대면 안 되는 레버다. 실무는 근거 자료
(매출계획·결제예정표)를 회의에 올리고 숫자 확정은 회의체가 한다.

## 3. 이관 전 상태의 결함

### 3.1 실무 입력이 브라우저에만 있었다
`fxRegimeInputs.ts` 의 수동 입력값은 `localStorage`(`fx_regime_inputs_{법인}_{통화}`)에
저장됐다. 서버에 없으므로 **정책회의 화면에서는 보이지도 않고 정정할 수도 없었다.**
담당자 A와 B의 PC에 서로 다른 값이 들어 있어도 아무도 알 수 없다.

### 3.2 정책 밴드가 연결되지 않았다
리짐 페이지의 정책 밴드는 위 localStorage 값이었고 `policy_params.fx_target_min/max`
와 무관했다. 정책회의가 의결한 밴드가 실제 권고에 반영되지 않는 상태.

⚠ **단위 불일치**: `fx_target_min/max` 는 DB 에 **%**(20)로, 리짐 엔진은 **0~1**(0.20)로
쓴다. 변환은 `fxRegimeInputs` 한 지점에만 둔다. 두 군데서 나누면 20% 가 2000% 로
들어가는 사고가 난다.

### 3.3 수동 입력 모드가 잠금 우회 경로였다
`수동 입력 / Treasury 연동` 토글로 총자금·보유액까지 임의 숫자로 바꾼 뒤 그 결과로
권고를 받을 수 있었다. 정책 필드를 잠가도 이 경로가 열려 있으면 우회가 된다.

## 4. 목표 구조

```
/fx-regime  (실무 일상 · 매일)              /policy › 💱 FX 정책 (회의체 · 분기 + 상시)
  ① 현재 국면   진단                          ① 적용 중인 정책 ── 밴드·프로토콜·5×3 목표표
  ② 환전 판단   집행                          ② 실무 현황 모니터링 ── 실무 화면 수치 + 정정
  ③ 규칙 검증   (백테스트)                    ③ 한도 계산기 ── σ×Z, 결과를 ①로 불러오기
  └ 정책 기준 탭 제거 → 읽기 전용 표시로 대체     └ FIFO 원장(/fx-ledger)은 독립 유지
```

### 정책 화면 ②탭에 표시할 모니터링 항목
1. 현재 국면·수준 → 적용 목표 잔존비중 vs 현재 비중 (밴드 오버레이 게이지)
2. 권고 환전액과 **미이행 경과일**
3. 미완료 매각 지시 D-day (`fx_trade_history.due_date`)
4. 환전 가능 재고(FIFO, 정기예금 만기 잠금 반영) vs 권고액 — 재고 부족 구분
5. 분기 손실실현 한도 소진율

계산은 전부 기존 SSOT(`policyChecks`, `usePolicyDashboard`, `useFxLots`) 재사용.

## 5. policy_params 키 정의

### 신규 (Phase 1)
| 키 | 단위 | 소유 | 설명 |
|---|---|---|---|
| `fx_ops_monthly_inflow_{cur}` | 외화 원금 | 정책 | 월 외화 유입 가정 (통화별) |
| `fx_ops_payable_{cur}` | 외화 원금 | 정책 | 향후 3개월 결제 버퍼 (통화별) |
| `fx_ops_loss_cap` | 원 | 정책 | 분기 손실 실현 한도 |
| `fx_ops_loss_used` | 원 | 실무 | 이번 분기 기실현 손실 |

`{cur}` 는 소문자 통화코드(`usd`/`eur`/`jpy`/`gbp`).

### 기존 재사용
`fx_target_min` / `fx_target_max` (%, 정책 소유),
`fx_regime_*` / `fx_level_*` (프로토콜 13개 + 5×3 목표표 + 앵커, 정책 소유).

### Phase 2 DDL
```sql
alter table policy_params
  add column if not exists overridden_by  text,
  add column if not exists overridden_at  timestamptz,
  add column if not exists override_note  text;   -- 정정 사유
```
소유권은 코드에 고정되므로 `value_source` 는 두지 않는다. 위 3개는 **감사 추적 전용**
(누가 언제 왜 바꿨는지). 정정 해제 기능도 없다 — 정책 소유 필드는 항상 정책 소유다.

## 6. 연동 재정의

- **`policyChecks.checkFx` 이원화** — `checkFxBand`(밴드 준수, 기존 로직) +
  `checkFxRegimeTarget`(리짐 목표 대비 이행). 대시보드·회의·의결 카드가 둘을 구분 표시.
- **`policy_decisions.linked_metric` 확장** — `fx_regime_target`, `fx_sell_order` 추가.
  기존 `fx_ratio`/`loan_ratio`/`liquidity` 동작 무영향.
- **이슈 자동 노출** — `makeIssueKey('policy'|'fx_sell')` 인프라 재사용해
  "리짐 권고 미이행 N일차" 를 대시보드 티커·자금일보 배너에 추가.
- **매각 지시 경로** — `fx_trade_history.order_type` 에 `'regime'` 추가해
  한도초과(`threshold`)·재량(`discretionary`)·리짐권고(`regime`)를 구분.

### Phase 4 산출물
- **판정 스냅샷** `src/lib/fxRegimeSnapshot.ts` — 대시보드·자금일보는 환율 이력 1,000여 건을
  매번 돌릴 수 없고, "권고가 언제 처음 났는지"를 기록할 곳도 없었다(§9 미결 사항).
  실무 화면이 판정할 때 결과 요약만 `policy_params` 에 남기고 다른 화면은 그 숫자만 읽는다.
  키: `fx_regime_snap_{target|current|suggest|since|asof}_{cur}`.
  `since` 규칙 — 조치 불필요→권고: 오늘로 설정 / 권고 지속: 유지(경과일이 늘어남) /
  권고→조치 불필요: 삭제. 변경이 없으면 아무것도 쓰지 않는다. 단위 테스트 6건.
  ⚠ 시뮬레이션 모드에서는 절대 기록하지 않는다 — 가정값이 전사 경보로 번진다.
- **`checkFxRegimeTarget`** — `checkFx`(정책 밴드 준수)와 **다른 위반**이다.
  밴드 안에 있어도 오늘 국면이 지시한 목표를 초과 보유할 수 있다.
- **`linked_metric: 'fx_regime_gap'`** — 리짐 목표 대비 초과 보유 폭(%p).
  통화가 여럿이면 가장 큰 초과 폭으로 판정한다. 스냅샷이 없으면 위반 없음(오탐 방지).
- **미이행 노출** — 대시보드 이슈 티커(`fx_regime_{법인}_{통화}`)와 자금일보
  `PendingRegimeBanner`. **1영업일 유예** 후 경보 — 당일 발생 권고까지 올리면 노이즈다.
- **`order_type: 'regime'`** + `src/lib/fxOrderType.ts` 라벨 SSOT.
  실무 화면 `환전 판단` 탭에서 `이 권고로 매각 지시 등록` → 기존 발의→승인→완료
  워크플로우에 그대로 태운다(기한 +3영업일). 화면 안 미리보기로 승인받는다
  (`window.confirm` 은 크롬 차단 시 조용히 false 를 반환 — 세션24차 실사고).

### Phase 2 산출물
- `src/hooks/useFxRegime.ts` — 시계열·프로토콜·컨텍스트·`evaluateRegime` 전 경로 SSOT.
  실무/정책 화면이 이 훅 하나를 공유한다. `autoSync` 는 실무 화면만 true(ECOS 중복 호출 방지).
- FX 정책 탭 서브탭: `① 🧭 리짐 이행 현황` / `② 🎯 정책 기준` / `③ 📐 한도 · 집행`.
  리짐 관련 서브탭은 **활성일 때만 마운트**한다 — 환율 이력·FIFO 로트 조회가 딸려 있어
  보이지도 않는 탭에서 미리 돌리면 불필요한 네트워크 비용이 든다.
- `FxRegimeMonitorCard` — 국면·수준·목표 게이지(밴드 오버레이), 권고액,
  **환전 가능 재고 vs 권고액**(재고 부족은 "실무 미이행 아님"으로 명시), 손실한도 소진율,
  미완료 매각 지시 D-day.
- `FxRegimeStandardTab` — `FxRegimeOpsCard` + `ProtocolTab`. 정책 기준의 유일한 편집 지점.
- `usePolicyParams.set(..., audit?)` — 정정 사유 기록. 감사 컬럼이 없는 환경에서는
  **값만 저장하고 1회 재시도**한다(사유 기록보다 의결값 반영이 우선).

### Phase 3 산출물
- 서브탭 4개로 확정: `① 🧭 리짐 이행 현황` / `② 🎯 정책 기준` / `③ 📐 한도 계산기` / `④ 🧾 매각 집행`.
  계산기와 집행을 나눈 이유 — 계산기는 **참고안을 만드는 도구**, 집행은 **실제 돈이 나가는
  워크플로우**다. 한 화면에 있으면 계산 결과가 곧 확정인 것처럼 읽힌다.
- **자동저장 제거**: 기존 `🎯 자동설정` 은 `window.confirm` 하나만 거치면 `fx_target_min/max`
  를 곧바로 저장했다. 리짐 채택 후 밴드는 리짐 목표비중을 가두는 제약이므로 계산기가
  단독으로 확정하면 안 된다. `📐 권고 밴드 계산` → `📥 정책 기준으로 불러오기` →
  ②탭에서 사유와 함께 저장, 3단계로 분리했다.
- 인계는 **부모 state(`bandDraft`) + 자식 `useMemo` 병합**으로 구현한다.
  effect+setState 로 초안에 밀어넣으면 캐스케이드 렌더가 생기고, 사용자가 값을 지워도
  계산기 값이 되살아난다. 부모 초안은 저장 성공·되돌리기 때만 비워, 서브탭을 오가도
  초안이 살아남는다.

**Phase 1 에 잠금을 포함시킨 이유**: 데이터만 서버로 옮기고 잠금이 없는 중간 상태를
만들면, 그 기간에 실무자가 정책값을 덮어쓸 수 있다. 같은 키를 두 주체가 쓰는
마지막-쓰기-승리 문제라 반드시 잠금과 함께 배포한다.

Phase 1 은 화면 구조를 바꾸지 않으므로 단독 배포가 가능하다.

## 8. 검증 기준

- **수치 정합**: 세 화면의 외화비중이 동일해야 한다 —
  `/fx-regime` 자금 입력 / `/policy` FX 정책 탭 / `/policy` 회의·의결 탭.
  (세션19차에 분모 불일치로 6.2% vs 27.9% 사고 이력)
- **잠금**: 실무 계정으로 로그인해 정책 소유 필드가 편집 불가인지 확인.
- **시뮬레이션 격리**: 시뮬레이션 모드에서 변경한 값이 새로고침 후 사라지고,
  실데이터 모드 권고에 영향을 주지 않는지 확인.
- tsc 0 errors / lint 0 errors / vitest 전체 통과 / build 성공 / 국면 엔진 50/50.
